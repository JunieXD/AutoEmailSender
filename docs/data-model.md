# 数据模型

桌面端本地数据（SQLite）的实体、状态和规则。表的列以迁移文件为准，这里只写迁移里看不出来的东西。功能本身见[总体设计](design.md)。

目标：表少而清楚，一件事只存在一处；高频查询都有索引，用实测证明够快（见[性能](#性能)）。

## 通用约定

- 编号：本地表用自增整数。要交给服务器或写进邮件的编号（邮件追踪编号、交给云端的邮件编号）另外生成随机值，不暴露本地编号。
- 表都用 `STRICT`；状态和类型存成文字，用 `CHECK` 限定取值。
- 没有值存 `NULL`，不存空字符串，"未填写"就是 `IS NULL`。
- 时间：时刻存 UTC 毫秒整数。用户说的"某天几点"（定时窗口的日期和起止时间、待办的截止时间）存成本地日期和时间，用的时候按系统当前时区换算成时刻。
- 状态：用 Rust 枚举表示，每种状态带着它要的数据，比如"已发出"一定有发出时间和 Message-ID；表里用约束保证状态列和这些字段一致。
- 能推出来的不存：任务进度、Token 合计都在查询时算。唯一的例外是[联系汇总](#联系状态)。
- JSON 只用在只整体显示、不按其中的值查询的小列表上（近期论文、定时的日期、收件人）。
- 邮箱地址按用户填的存，比较时不区分大小写。
- 大字段（邮件正文、页面文字、材料文字）列表查询不取，用到时再取。
- 文件：材料存在数据目录的 `materials` 里，文件名用材料编号；数据库只存元数据和提取的文字。添加时先写临时文件，改名后才提交数据库记录；删除时先删记录再删文件。中途退出最多留下一个用不到的文件，不会有没有文件的材料。
- 日志在数据目录的 `logs` 里，用到应用的每一天一个文件，保留最近 14 个。升级数据库前的副本在 `backups` 里，保留最近 3 份；新建的数据库不用备份。

## 实体

### 个人资料和配置

- 个人资料：姓名、意向研究方向、草稿改写偏好、信件样式、轮转策略、默认模型配置（没设时用最早添加的）和默认模板，以及各项开关（AI 核对、AI 标记回信结果、回信待办、邮件追踪、云端备份）。
- 邮箱：地址、发件人名称、服务商、服务器设置、登录方式、每日上限、最短间隔、轮转顺序、暂停到什么时候和原因，上一轮收信出错的原因和被拒绝后什么时候再试。密码、授权码和 OAuth 令牌存在单独一列，只有收发信时读取，不出现在界面拿到的数据里。
  - 收信进度另有表记录：每个文件夹的 UIDVALIDITY 和处理到的 UID，以及补查队列（每个邮箱还要补查哪些导师邮箱）。导师加了邮箱时，由触发器把这个地址加进每个邮箱的补查队列；删掉的地址一起移出队列。邮箱改了地址或收信服务器，触发器清掉它的收信进度，下一轮重新开始。
- 模型配置：名称、服务商或自定义地址、模型名、单价、是否已确认发送说明（换了服务商或接口地址就要重新确认）。可以有多个，其中一个是默认。API Key 存在单独一列，只有调用模型时读取。
- 材料：文件名、大小、文件、提取的文字、用途（匹配分析、写信参考、默认附件）。文件存下后不再改，换文件就是新材料；一个文件不超过 20 MB。没提取到文字的只能作附件。
- 模板：名称、主题、正文（Markdown）。
- Token 用量：每调用一次模型记一行（服务商没有报告用量的不记）：时间、模型配置、模型名、用途（抓取、匹配、草稿、改写、核对、回信标记、回信待办、起草回复）、关联的抓取或邮件，以及输入、缓存命中和输出的 token 数。

### 导师

- 导师：姓名、来源网址、负责邮箱、匹配结果；在回收站里的带着移入时间。邮箱、单位、主页、别名和导师库记录一位导师可以有几个，各放一张表，按用户排的顺序。研究方向、近期论文、个人备注和匹配理由这些长文字放在 `mentor_detail` 表，列表扫描和排序只碰短的行。
  - 邮箱：地址在所有导师中唯一，也可以一个都没有。排第一的是发信地址，首封、追问和回复都发到它；其余的用来认出导师从这些地址发来的信，和补查以前的往来。程序替用户加地址时（接受候选导师、导入、合并导师、把来信地址加为导师邮箱），学校的地址排在其他地址前面：域名有一级是 edu 或 ac 的算学校的，如 pku.edu.cn、ucas.ac.cn、mit.edu、ox.ac.uk。用户在表单里排的顺序照用。
  - 单位：学校、学院、系所和职称一组，至少填一项；职称跟着单位走（在 A 学院是教授，在 B 研究院是兼职教授）。排第一的是主要单位，列表、导师详情的标题和模板的占位符用它；筛选、关键词搜索和统计算全部单位。
  - 主页：几个网址，比如学校的主页、个人网站、Google Scholar。
  - 别名：关键词搜索能搜到；发送前检查看有没有称呼导师时，称呼别名也算；AI 写信时和姓名一起发给模型。
  - 导师库记录：一般一条；合并来的导师可以对应几条。
  - 匹配结果：每位导师只留最新一次，是导师表上的一组列：状态（排队、分析中、完成、失败）、分数、分析时间、所用模型、失败原因；理由、契合的方向、可强调的经历、风险点在 `mentor_detail`。重新分析覆盖上一次。匹配模块通过导师模块的函数写入。
  - 关键词搜索：姓名、别名、各个单位的学校、学院和系所，以及研究方向拆成相邻两个字一组，写进 FTS5 全文索引；词与词之间隔开，短语不会从一个词连到下一个词。搜索时把关键词也这样拆开，按短语查，结果就是"包含这个词"。两个字以上的中文和英文都能用索引。一个字的词只查姓名和别名：它们的每个字另外单独写进索引的一列。
  - 导师用资料里没有的地址回信时，靠邮件头里的 In-Reply-To 和 References 归到这位导师，往来里可以把这个地址一键加为导师的邮箱。
  - 负责邮箱：联系这位导师用的邮箱。用户可以手动指定；没指定时，第一次发出（包括可能已发出）或第一次在邮箱里找到往来时记下，明确没发出的不算。追问和回复只用它发。
- 标签：名称、颜色、顺序；导师和标签多对多。
- 导师库更新：从导师库导入的导师，记录有更新时，本地空着的字段直接补上，邮箱、单位、主页和别名加上本地没有的；和本地不同的字段记成待处理的更新，由用户逐项选；退休、离职这类变化只提醒。
- 合并导师：见[合并导师](#合并导师)。

### 联系

- 任务：名称、类型（首封或追问）、写法（AI 生成或套用模板，含所用模板和模型配置）、写信参考材料、附件、发送方式（立即，或定时：日期、时间窗口、每个窗口的数量）、暂停或停止。进度由邮件状态推出。
- 邮件：应用写的每一封信，属于一位导师。批量的属于一个任务；单独写的和回复导师的不属于任务。
  - 类型：首封、追问、回复。追问和回复记着回的是哪封信，发出时据此写好 In-Reply-To 和 References，留在原线程里。二次联系是新的首封。
  - 导师详情里没写完的首封，就是这位导师一封不属于任务、待审核的首封邮件，每位导师最多一封。
  - 往来下方输入框里没写完的回复，就是这位导师的一封待审核的回复邮件，每位导师最多一封；按"发送"时直接批准。
  - 草稿存 Markdown，附件记在附件清单里（材料编号、文件名和大小），同一封信里文件名不重复。批准时存下渲染好的 HTML 和纯文本，附件清单换成批准时的，之后不再变。
  - 发出时记下发件邮箱和地址、收件地址（交出时导师的发信地址）、所用模型名、Message-ID、发出时间。
  - 退信的邮件可以重新发送：新建一封内容和附件相同的邮件，类型和回的信不变，发到导师现在的发信地址；原来那封保留退信记录。删除邮箱或模型配置后，地址和模型名还在。
  - 在发件邮箱的"已发送"里找到副本时记下副本的 Message-ID：服务商可能给副本换一个（QQ），回信和退信按两个都认。
  - 开了邮件追踪的带一个随机的追踪编号；打开次数和首末次打开时间从服务器拉回来。
- 来往邮件：邮箱里看到的、不是应用发出的信，比如导师的回信、自动回复、用户在网页上发给导师的信。记所在的邮箱、文件夹和 UID，Message-ID、In-Reply-To、References、发件人、主题、时间和纯文本的正文，以及是否只读了开头。时间用服务器收到的时间（INTERNALDATE），没有时用信头的 Date。
  - 一封可以属于几位导师。在别处发给几位导师的信被退回时，退信原因记在被退的导师名下。
  - 同一封邮件只存一份：有 Message-ID 的按它认，没有的按邮箱、文件夹、UIDVALIDITY 和 UID 认。
  - 应用发出的信在"已发送"里的副本不另存，只用来确认它已发出。
  - 收到退信时，按退信里原信的 Message-ID 找到被退的那封，标上退信和原因；退信本身不存。
  - 导师的回信带着已读时间（在应用里点开的时间）和回信结果（有意向、无名额、拒绝、无法判断，由 AI 标出或用户修改）。
- 待办：内容、截止时间（本地日期，可以带时间）、完成时间、属于哪位导师、从哪封回信提取（手动添加的没有）、是否已提醒。

### 抓取

- 抓取：一次智能抓取（学校、学院、起始网址、模型配置），或 Agent 的一次提交。状态有运行中、已暂停、已完成、失败、已取消。每次开始或继续记一条运行记录（起止时间、应用版本）。
- 访问过的页面：网址、抓取方式（HTTP 或 WebView）、结果、提取的文字。
- 候选导师：和导师相同的资料字段，其中邮箱、单位、主页和别名是列表，存成 JSON，加上审核状态（待审核、已接受、已拒绝、已合并）和信息补全状态。已接受和已合并的记着对应的导师。

### 其他

- 已配对设备：名称、公钥、配对时间、最近连接时间。撤销配对就是删除。

## 邮件状态

| 状态 | 含义 | 接下来 |
|---|---|---|
| 生成中 | AI 正在写草稿 | 待审核、生成失败 |
| 生成失败 | 带着错误原因 | 生成中 |
| 待审核 | 有草稿，等用户批准 | 已批准、已取消 |
| 已批准 | 正文已定，带着计划发送时间，等时间到、邮箱有余量 | 发送中、发送失败（没能登录邮箱）、云端待发、待审核（改回草稿）、已取消 |
| 云端待发 | 已交给官方服务器 | 已发出、可能已发出、发送失败（结果从服务器同步回来）、已批准（撤回到本地） |
| 发送中 | 已交给 SMTP | 已发出、可能已发出、发送失败 |
| 可能已发出 | 发送途中连接中断或应用退出，说不清发没发出，带着原因 | 已发出（在"已发送"里找到）、已批准（用户确认没发出，手动重发） |
| 已发出 | | 退信 |
| 退信 | 带着退信原因 | —（重新发送是另一封已批准的新邮件，记着重发的是哪一封；一封只能重发一次，重发的那封也不能改回草稿） |
| 发送失败 | 没能登录邮箱，或 SMTP 明确拒绝，带着错误原因 | 已批准（重试）、待审核（改回草稿）、已取消 |
| 已取消 | 带着原因：移出任务、任务停止、导师移入回收站 | — |

发送计划的"待处理"一栏是：生成失败、发送失败、可能已发出，以及错过了时间窗口还没发的已批准邮件。

## 联系状态

由邮件和来往邮件推出，从上往下取第一个满足的：

| 状态 | 条件 |
|---|---|
| 已回复 | 有这位导师的回信，自动回复不算 |
| 退信 | 没有回信，最近一封发给这位导师的信被退回 |
| 已联系 | 有已发出或可能已发出的邮件，或用户在别处发给这位导师的信 |
| 未联系 | 其余 |

- 联系次数：首封邮件，加上在别处发出、不是回复的信，追问和回复不算。
- 最近联系时间：最近一封发出的信的时间。
- 发出后若干天没回复：最近一封发出的信之后没有回信，且距今超过这些天。
- 红点：这位导师有回信（自动回复不算）还没有已读时间，并且这封回信之后没有发给这位导师的信，应用发的和在别处发的都算。未读数是有红点的导师数。

怎么存：视图 `mentor_contact_live` 按上面的规则从邮件和来往邮件现算，这是唯一的定义。现算的耗时随邮件数增长（6 万封时首页要 85 毫秒以上），所以把结果存进 `mentor_contact` 表，每位联系过的导师一行，首页按它筛选和排序。

- 这张表只由触发器写：邮件、来往邮件或它们和导师的关联一变，触发器就按视图重算受影响的导师，在同一个事务里完成，每次约 0.04 毫秒。应用代码不写它。
- 测试在各种操作后检查这张表和视图逐行相同。

## 后台任务的进度

| 后台任务 | 进度存在哪 |
|---|---|
| 抓取 | 抓取的状态、访问过的页面、候选导师 |
| 匹配 | 导师的匹配状态 |
| 批量草稿 | 邮件的生成中状态 |
| 收信 | 文件夹的收信进度和导师邮箱的补查队列 |
| 定时发送 | 已批准邮件的计划发送时间 |

## 删除

| 删除什么 | 结果 |
|---|---|
| 导师移入回收站 | 资料保留，可以恢复。没发出的邮件取消，恢复后不会自动恢复 |
| 永久删除导师 | 只能在回收站里做。导师的邮件、只属于这位导师的来往邮件、匹配结果、待办和标签关系一起删除，统计里不再算。邮箱里的原始邮件不受影响 |
| 删除任务 | 没发出的邮件一起删除；发出过的留在导师的往来里 |
| 删除邮箱 | 发出过的邮件保留发件地址；以它为负责邮箱的导师改为未指定，之后按轮转重新选 |
| 删除模型配置 | 历史记录保留模型名；用它的任务改用默认模型配置 |
| 删除材料 | 待发送、发送中、可能已发出、发送失败的邮件用它作附件时不能删；草稿里的这个附件一起去掉；发出过的邮件保留附件文件名 |
| 删除模板 | 已经生成的草稿不受影响 |
| 删除抓取 | 访问过的页面和没处理的候选导师一起删除；已经进了导师管理的导师不受影响 |

## 合并导师

同一位导师在列表里出现了两次（比如从两个学院分别抓到），用户把其中一位并进另一位。在一个事务里完成：

| 内容 | 合并后 |
|---|---|
| 姓名 | 保留的导师的；另一位的姓名不同时记为别名 |
| 邮箱、单位、主页、别名、代表论文、标签、导师库记录 | 两位的合在一起，保留的导师的在前，重复的只留一个 |
| 研究方向、来源网址、负责邮箱、匹配结果 | 保留的导师有就用它的，没有用另一位的 |
| 备注 | 两位都有时接在一起 |
| 邮件、来往邮件、待办 | 都归到保留的导师，联系状态按合并后的重算；同一封来往邮件两位都有的，只留一份 |
| 没写完的首封和回复 | 两位都有时留保留的导师的，删掉另一位的（合并前说明） |
| 候选导师、导师库的待处理更新 | 改为对应保留的导师 |

- 有还会发出的邮件时不能合并：任务里没发出的、已批准、云端待发、发送中、发送失败的。先发出、取消或移出任务。
- 在回收站里的导师不能合并。
- 另一位导师合并后直接删除，不进回收站。

## 性能

预算：本地 10 万位导师、6 万封邮件、2.5 万封来往邮件时，打开首页的一页（导师、总数和标签）不超过 30 毫秒，写一封邮件的状态不超过 1 毫秒。真实用户的数据量远小于这个规模。

`cargo xtask bench` 在 Apple Silicon Mac 上的实测（每项取 15 次的中位数）：

| 查询 | 耗时 |
|---|---|
| 首页，第 1 页 / 第 100 页 / 第 1900 页 | 2 / 2 / 3 ms |
| 首页，按联系状态筛选 | 5–11 ms |
| 首页，关键词命中少 / 命中七成以上 / 一个字 / 一个字加一个词 | 8 / 17 / 3 / 4 ms |
| 写一封邮件的状态 | 0.1 ms |

还没实现的查询在原型上测过：按学校、标签、没回复天数筛选 5 ms 以内；红点数、往来、发送计划 0.1 ms 以内；统计（每日发送量、各校回复率）39 ms。

做到这些靠的是：

- 首页排序用的匹配分数在导师表上，和回收站时间、编号一起建索引，翻页不用把全部导师排一遍。
- 长文字和列表要用的列分开放。
- 联系状态存成由触发器维护的汇总表，不用每次汇总全部邮件。
- 筛选条件只引用导师表，联系状态和关键词写成 `IN` 子查询；给每位导师连接一次汇总表，数 10 万位导师要慢 10 倍。先在导师表上取出一页，再连接详情和联系汇总，翻到后面的页也不变慢。
- 关键词搜索全走全文索引，一个字的词查姓名单字那一列，不用 `LIKE` 扫描。

改表结构或高频查询时，按[开发约定](development.md#数据库)重新跑一遍基准。
