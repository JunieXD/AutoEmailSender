# 社区导师投稿与抓取 CLI 优化执行计划

## 目标与范围

把“智能抓取任务 -> 资料补全 -> 导入本地导师库 -> 导出社区投稿包 -> 维护者提交 -> 审计恢复”变成可重复、可恢复、低 Token、低浏览器依赖的工作流。

## 实施进度

- [x] 阶段 0：固定社区安全列、批次合同和 CLI 回归基线。
- [x] 阶段 1：投稿 Skill、manifest 准备/审计/提交 dry-run 脚本。
- [ ] 阶段 2：维护者 PR intake 的真实远程演练和恢复验证。
- [ ] 阶段 3：更多跨任务批量选择与状态读取入口。
- [ ] 阶段 4：完整后端/桌面回归和性能验证。

本轮明确不做：学校/学院列表页发现、列表页审核台账、通用学校学院数据血缘系统。范围只覆盖智能抓取相关 CLI 和社区投稿。

## 当前问题基线

- 社区导出虽已有 `professors.community.export-package`，但主要依赖逐个传入导师 ID，不能按抓取任务、学校/学院或排除项直接生成投稿批次。
- `crawler.jobs.create-many`、`crawler.jobs.enrich-many` 已能批量工作，但候选审批和后续导入仍需要模型搬运大量 ID，容易产生上下文和重试成本。
- CLI 能力发现对“社区投稿/贡献/共享包”等中文复合意图召回不稳定，可能返回无关命令。
- 外部写入出现未知结果时，缺少稳定的批次指纹和恢复命令，容易误重试或重复投稿。
- GitHub Issue Form 的本地附件上传没有稳定的 `gh issue create` 参数；浏览器自动化可以工作，但速度慢、脚本脆弱、需要逐份操作。
- 大结果集如果直接输出 stdout，会浪费 Token；现有文件导出、分页和 `wait` 能力需要组合成更高层的工作流。

## 交付结果

1. 一个仓库内维护的 `submit-mentors-to-community` Skill，支持显式调用，也能准确匹配“投稿/社区导师库/批量提交”等请求。
2. 一套确定性投稿脚本：准备、校验、提交、审计、恢复；脚本输出机器可读 JSON 和人类可读摘要。
3. 一个维护者专用纯 CLI 投稿通道，优先使用 `gh` 创建/查询 Issue 或 PR，不依赖 ego-lite；普通社区用户的 Issue Form 流程保持兼容。
4. 一个社区投稿批次 manifest，记录学校/学院、导师数、文件路径、SHA-256、目标 Issue/PR、状态和错误，不把大表格或大量 ID 放进模型上下文。
5. CLI 批量选择与状态读取的增量改进，支持冻结选择、按抓取任务引用、批量审批/等待/导入，并保留现有命令兼容性。
6. 完整测试和恢复演练，不引入现有抓取、补全、导入、社区导入回归。

## 分阶段执行

### 阶段 0：合同和基线

- 阅读并固定现有 `capabilities`、`describe`、抓取任务、补全、审批、导入、社区导出合同。
- 补充回归测试：能力发现、错误码、分页/文件导出、任务终态和社区安全列校验。
- 定义 manifest v1、批次状态枚举和稳定批次指纹。
- 验收：现有 CLI 测试通过；旧命令输出和风险确认语义不改变。

### 阶段 1：仓库 Skill 与确定性准备脚本

- 新增 `.agents/skills/submit-mentors-to-community/SKILL.md` 和 `agents/openai.yaml`。
- 新增 `scripts/prepare_submissions.py`：按已导出的社区安全数据分组、去重、校验文件大小/列、生成 manifest。
- 新增 `scripts/audit_submissions.py`：校验 manifest、文件 SHA-256、Issue/PR 映射和重复批次。
- Skill 只描述路由、授权、停止条件和脚本调用；可变 GitHub/API 细节放到 references。
- 验收：Skill 通过 `quick_validate.py`；脚本在无网络测试夹具上可重复运行。

### 阶段 2：维护者纯 CLI 投稿通道

- 首选维护者 PR intake：把已校验 proposal set 提交到稳定分支，用 `gh pr create` 创建审核 PR。
- 如果仍需公开 Issue 记录，使用 `gh issue create` 创建轻量索引 Issue，正文引用批次 manifest/PR，而不是上传多个附件。
- 所有外部操作使用批次指纹、标题标记和查询优先的恢复策略；未知结果时先查重，禁止盲目重试。
- 保留现有 Issue Form，避免破坏普通贡献者流程；两条入口最终进入同一校验/审核管线。
- 验收：本地 dry-run、真实单批次试投、重复执行不产生重复 Issue/PR、网络失败可恢复。

### 阶段 3：CLI 批量选择和任务链改进

- 增加可冻结的 selection 引用，避免在命令间搬运大量导师/候选 ID。
- 支持按抓取任务批量选择候选、批量生成审批计划、批量等待、批量导入，并返回失败项和下一动作。
- 增加面向社区的批量导出入口：按任务或结构化筛选生成多文件包和 manifest，自动排除已有社区记录。
- 为 capabilities 增加社区领域同义词和复合意图测试，低置信时返回明确的无匹配结果。
- 验收：大批次 stdout 只返回摘要；完整数据写文件；中途失败可从 selection/manifest 继续。

### 阶段 4：性能、安全与回归验证

- 用 `gh` API 查询代替浏览器读取 Issue 状态；浏览器仅保留附件上传兼容路径。
- 对外部文本只当数据处理；token、密码和原始日志不进入 manifest 或 Skill。
- 运行后端 CLI/社区/抓取测试、脚本测试、Skill 校验和一次真实小批量投稿演练。
- 对最终变更执行影响范围检查，确认没有改变邮件发送、导师导入确认计划和抓取运行时行为。
- 验收：所有相关测试通过；真实投稿可审计、可恢复；没有重复投稿。

## 提交策略

- 阶段 0/1 完成后提交一次：计划、Skill、manifest/准备/审计脚本及测试。
- 阶段 2 完成后提交一次：维护者 CLI 通道及恢复测试。
- 阶段 3/4 完成后提交一次：CLI 批量选择、能力发现和最终回归。
- 每次提交只包含本阶段文件；保留工作树中用户已有的无关改动。

## 明确不采用的方案

- 不依赖 GitHub Issue Form 的未公开内部上传接口作为长期协议。
- 不把 48 个文件、数千个导师 ID 或外部网页正文直接放入模型上下文。
- 不通过自动重试掩盖外部写入的未知结果。
- 不在本轮建设学校学院发现台账或全局数据血缘系统。

阶段 0/1 已落地的入口：

- `.agents/skills/submit-mentors-to-community/`：Skill、投稿合同和恢复说明。
- `prepare_submissions.py`：生成不含绝对路径的稳定批次 manifest。
- `audit_submissions.py`：重新计算文件指纹、人数和 batch_id。
- `submit_submissions.py`：默认只生成 `gh`/`git` PR 计划，`--execute` 才允许维护者写入。
- `professors community export-package --professor-id-file`：从冻结选择文件导出共享包，兼容原有重复 `--professor-id`。
